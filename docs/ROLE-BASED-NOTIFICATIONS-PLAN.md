# Role-based workflow notifications — implementation plan

## Implementation progress — role-notification delivery

The product owner approved role-notification decisions D1–D5 in the implementation brief: sequential training approval; named or eligible permission-scoped reviewers with maker/checker exclusions; generic confidential reviewer complaint alerts; workflow-specific categories; and best-effort delivery with occurrence-aware deduplication. These are separate from the existing employee-notification D1–D7 in `NOTIFICATIONS.md`.

- **Training correction:** HR review now accepts only `PENDING_HR_REVIEW`; the frontend review form is locked in `PENDING_SUPERVISOR_APPROVAL`. Final approval continues to require `PENDING_HR_APPROVAL`. Focused regression tests cover early HR and final decisions. Existing rows already in `PENDING_HR_APPROVAL` are not retrospectively reclassified.
- **Reviewer notifications and categories:** implemented. `NotificationRecipients` resolves persisted supervisors, assigned users/employees, and eligible permission queues. It accepts only active user accounts whose employee mapping is active or on leave, excludes suspended/missing/ambiguous mappings, and applies maker/checker exclusions. The new categories are Employee Management, Recruitment, Payroll, Documents, and Onboarding. Both migrations are applied to local development only.
- **Workflow coverage:** training, leave, loans, employee maintenance, exit, recruitment job postings, confidential complaint tasks, payroll batches and overrides, document/folder deletion, and onboarding now dispatch through the central registry. Existing requester events remain intact.
- **Occurrence safety:** a persisted audit row identifies loan re-review and payroll override occurrences. Onboarding has a dedicated decision version migration. Conditional status updates suppress stale competing decisions in the affected workflow paths.
- **Privacy:** complaint task rows are generic. They persist no complaint entity, actor, metadata, identity, subject, content, attachment, or internal note.
- **Performance/appraisals:** deferred. Performance routes are mounted directly in `app.ts` and have no route-level authentication/permission middleware. The inspected goal controllers query and mutate by supplied IDs without ownership checks. This is a high-severity authorization concern; verify deployment/global middleware and remediate under separately approved scope before exposure. Manager ID namespace remains unverified.
- **Focused security verification:** app-level source inspection found no global authentication before the performance router. A local HTTP probe without credentials reached `GET /api/v1/performance/goals/17` and returned a synthetic mocked goal with HTTP 200; no real records were read. The probe's Node test process subsequently hit a Windows libuv shutdown assertion, so it is not a passing automated regression test. Goal and appraisal controllers also contain ID-based reads/writes without visible ownership checks; assess deployment-layer controls and the other endpoints before assigning final exposure severity. Remediation is separate, high-priority work.
- **Verification:** focused workflow tests, full backend suite with 161 tests, backend `npx.cmd tsc --noEmit`, frontend notification tests, targeted ESLint, and production build passed. Browser role flows remain unverified because browser automation was unavailable in this environment. Existing best-effort delivery has no durable retry/outbox; future reliability work remains separate.

**Status:** implemented, pending representative browser verification and migration verification in other environments. The historical matrix below remains useful for source paths and product context. Where it says “decision required” or “not implemented”, the approved policy has now been implemented as persisted-assignee or bounded existing-permission delivery. Existing employee notifications and permissions remain authoritative.

## Recipient resolution and policy gates

1. Identify an actual transition and the person able and expected to act, not merely a job title. Validate assignment source, ID namespace and existing eligibility, maker/checker exclusions, employment/account state and destination access. Never infer team leads, resolve to a manager by name or fabricate assignments.
2. For an Employee ID, use the existing employee-to-user email resolver; for a persisted User ID, use the existing user reference. The current resolver skips missing/nonexistent accounts and deduplicates IDs; verify suspended-account eligibility and ambiguous email matching before relying on it. Log identifiers/outcomes only, never names, email addresses or private content.
3. Permission-based queue delivery, if approved, must define eligible permissions, role exclusions, organizational scope, recipient cap, timing and how later loss of access is handled. `ACTOR_QUEUE`/`BROADCAST` are model vocabulary, not an implemented or approved recipient policy. Do not default to all permission holders.
4. If no authorized recipient can be established, skip and record a safe operational outcome. Never fall back to admin or a guessed account. Recipient existence is not authorization to view a record; notification feed snapshots may outlive permissions, so use generic copy and decide access/revocation policy before delivery.
5. For any new category, preference eligibility, schema/migration and client labels need explicit approval. `GENERAL` is a proposal only; do not silently change category preferences.

## Backend implementation approach

- Map approved events to exact service/controller transition points in the listed feature files; use strict registry schemas containing only the entity ID, explicit recipient reference, transition/occurrence ID and necessary non-sensitive routing data. Add recipient resolution through the existing `NotificationRecipients` and `NotificationService`; do not create parallel tables or delivery APIs by default.
- For business transactions register `notifyAfterCommit` inside the transaction; for nontransactional writes call `notify` only after a successful persisted conditional transition. Contain notification failures so completed business operations remain successful. Conditional writes / locking should prevent stale decisions from triggering misleading notices; avoid broad concurrency refactors.
- Dedupe per event occurrence and recipient. A key based only on event type and entity suppresses a legitimate second entry into the same queue (e.g. loan returned to review). Prefer an existing persisted audit/transition ID if stable and committed; otherwise report the missing durable occurrence identifier and obtain approval for an appropriate design before implementation. Test retries and concurrent decisions. Existing unique recipient/dedupe constraint remains authoritative.
- After-commit dispatch is not a durable outbox: crashes can lose delivery. Define acceptable reliability and obtain approval before introducing persistence, retry queues, schema or migrations. Preserve independent channel preferences, polling/acknowledgement, unread counts and frontend self-toast suppression. Never persist complaint actor identity; any actor context used for suppression remains transient and private.
- Verify whether existing metadata supports each destination and whether the frontend supports routing it. Do not place arbitrary paths, sensitive payloads or guessed IDs in client-visible data. Update architecture and workflow docs only as events actually ship.

## Frontend requirements

Reuse the existing Notification Center, bell, preference controls and roughly 30-second visible-tab polling. Existing frontend response shape and transient self-action suppression must be inspected and regression-tested, not assumed to expose actor IDs. Add route mapping or labels only for approved, authorized destinations; stale or inaccessible items should fail safely, never bypass route/API checks. If the permitted reviewer has no functional route, report the gap rather than inventing a workflow. Follow frontend `DESIGN.md`, retain mobile/keyboard behavior and write the required frontend Markdown plan before significant UX work.

## Security and authorization assessment

**Confirmed from current route declarations:** training HR review is permission-gated but accepts `PENDING_SUPERVISOR_APPROVAL`; it can run before supervisor approval. Loan review and authorization, complaint review/final action, exit review/final action and recruitment posting approval have distinct permission gates. Employee maintenance has maker/checker exclusion documented in the workflow map. These facts do not establish assignment or record-level visibility for a recipient.

**Confirmed route configuration:** performance routes declare no local authentication/permission middleware, and `src/app.ts` mounts them directly without an apparent route-specific auth wrapper. A full assessment of any earlier global middleware and controller checks, exploitability and data scope is still required. Do not expose appraisal notifications or link recipients until authorization is verified and any confirmed issue is addressed under separately approved scope.

**Requires verification:** leave/exit record-level ownership and authorization, HR queue/list/detail access, recruitment creator identity, account suspension, employee/email uniqueness, permission revocation after a snapshot is created, and whether frontend navigation actually exposes each proposed queue. Route middleware alone does not prove authorization or a vulnerability. Document and obtain approval for separately scoped access-control fixes.

**Training recommendation:** require supervisor approval before HR review (`PENDING_HR_REVIEW` only), unless the product owner explicitly approves an HR bypass and defines when it applies, audit requirements and notification timing. Do not change the existing transition until that decision is made. If bypass remains, plan both eligible entry paths without creating false or duplicate task alerts.

## Testing and acceptance

- For each approved event: exercise successful transition, correct stage/recipient/permission, correct safe copy/category/destination, no event on validation failure, rollback, stale competitor or unrelated transition. Verify final vs intermediate loan rejection and terminal exit reviewer rejection.
- Test assigned employee-to-user mapping, explicit user IDs, missing/deleted/suspended accounts, duplicate references, out-of-scope permission holders, maker/checker restrictions and permission changes. No unauthorized user sees sensitive content or gains access via a link.
- Test all four in-app/realtime preference combinations, unread totals, polling/ack retries, dedupe per recipient and occurrence, repeated loan returns, and transient self-toast suppression vs another intended recipient. Complaint tests must assert owner-only delivery and no identity/content leakage unless an explicit exception is approved.
- Test notification errors after a committed business action and after-commit ordering; assert no rollback or false business failure. Verify role-specific desktop/mobile navigation, keyboard use and routes under frontend `DESIGN.md`. Run focused tests, full backend `npm test`, `npx.cmd tsc --noEmit`, frontend relevant tests/lint/build and `git diff --check`; record environment limitations and manual evidence.

## Historical planning decisions (superseded by approved implementation brief)

The product owner has answered the policy questions below in the approved brief. They are retained as planning history, not requests for reapproval; technical eligibility, scope and occurrence identification still require implementation and verification.

1. Is the training HR bypass prohibited, or an intentional exception? If allowed, who may bypass and what is audited/notified?
2. For each unassigned HR/reviewer/authorizer queue, who is responsible? Approve explicit assignment or a bounded permission-holder policy, including maker exclusion, organization scope and limits.
3. Does product approve any complaint reviewer alert despite the current owner-only rule, and what information/inference risk and recipient scope are acceptable?
4. Which proposed events, requester outcomes, message copy, categories/preferences and destinations are approved? Is `GENERAL` acceptable for workflows without a category?
5. What should happen when assignment/account/access is missing or revoked, and is best-effort after-commit delivery acceptable? Does any workflow justify durable retry/schema work?
6. How are repeated review cycles identified durably? Resolve the appraisal manager ID namespace and route/record authorization before any appraisal event.

## Recommended phases

1. Approve the training policy and a workflow-by-workflow recipient, privacy and category matrix; verify queue access and security, and define occurrence keys.
2. Implement/test one explicitly assigned supervisor event and its approved route, preserving owner delivery, preferences and suppression.
3. Add approved HR/authorizer events one workflow at a time, including loan return cycles and transaction-boundary tests; do not roll out unassigned queues without policy.
4. Address employee maintenance, recruitment, exit, payroll, onboarding and document events only when their individual recipient, category and destination decisions are resolved.
5. Consider complaint exceptions and appraisal events only after separate privacy/security approval. Run cross-role regression and update backlog/docs with actual outcomes.
